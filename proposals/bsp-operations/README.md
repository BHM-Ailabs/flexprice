# Disk attribution and retention — proposed operator follow-up

No SQL or filesystem query could run on production in this session: Railway SSH has no registered key and PostgreSQL has no public endpoint. Do not create either without separate operator authorization. `railway run` executes locally and does not make `.railway.internal` resolvable. Do not confuse lack of access with a zero-size database or proof of a WAL problem.

When an approved existing shell/connection is available:

- Execute `disk-audit.sql` using `psql -X -v ON_ERROR_STOP=1`, with credentials supplied only through the existing environment. Run per database (including Temporal and visibility if colocated); `pg_database_size` already includes that database's relations/indexes, so do not add the two together.
- On the container, read-only `df -m /var/lib/postgresql/data`, `du -x -m -d 2 /var/lib/postgresql/data`, and `du -x -m -d 2 "$PGDATA/pg_wal" "$PGDATA/pgbackrest-spool"` (if they exist). Compare `base/`, `global/`, `pg_wal/`, spool and logs against filesystem usage. A failed `du` path is not zero; PG18 can use a versioned PGDATA subdirectory. Do not `cat` configuration or `printenv` because credentials may be embedded.
- Repeat sizes daily for seven days; sample `pg_stat_wal.wal_bytes` and archiver counters twice with timestamps for WAL production/archive throughput. A WAL production rate is not net disk growth. Relation estimates are not exact bloat measurements.

## Conditional tuning, after attribution and a tested recoverable backup

Financial subscriptions/invoices/payments/ledger rows must follow an operator-approved accounting retention policy. Never mass-delete them to recover disk. For logs, webhook payloads and completed workflow history, inventory size and replay/audit requirements, then propose partition expiry or bounded batches only after that policy is approved. Temporal history retention is namespace policy; use the narrow completed-history retention the billing support/replay window requires, not a table-wide SQL delete. This PR changes no retention or schema.

Keep autovacuum enabled. On genuinely high-churn operational tables, evaluate per-table vacuum/analyze scale factors around 0.05/0.02 with practical minimum thresholds (e.g. 1000/500 tuples), compared with measured churn; tune workers/I/O to the service budget. Ordinary vacuum reuses space within the file and generally does not shrink the filesystem. `VACUUM FULL`, manual WAL deletion and broad reindexing are not incident shortcuts; they need locks/headroom and separate planning.

If WAL is the dominant local consumer, first resolve archiver failures or abandoned replication slots. PostgreSQL `max_wal_size` is a soft checkpoint target, not an absolute cap; archive failures and replication slots can keep WAL indefinitely. For the 20 GB volume, a candidate starting budget is `max_wal_size=1GB`, `min_wal_size=80MB`, checkpoint timeout 5 minutes and completion target 0.9, **only after measuring checkpoint load and actual retention requirements**. Bound slot retention only after confirming active replica/recovery needs; invalidating an active replica is a real availability tradeoff.

Read-only inspection of variable presence at 17:05 UTC found **both `WAL_ARCHIVE_BUCKET` and `WAL_RECOVER_FROM_BUCKET` absent**, and no numeric overrides for drop/queue/archive-timeout/backup-retention. This makes opt-in pgBackRest archiving less likely as the cause; persisted SQL configuration and actual `pg_wal`/spool bytes are still unverified. A startup sizing message alone is not evidence of enabled archiving.

The [Railway postgres-ssl image](https://github.com/railwayapp-templates/postgres-ssl) enables pgBackRest only when `WAL_ARCHIVE_BUCKET` is set. Upstream computes archive queue/drop thresholds from volume size (half volume, capped at 5 GiB). The observed startup line contains a blank `wal-drop=` and `queue-max=5120 MiB`; that does not establish the historical thresholds, enabled archiving, cause of growth, or successful backups. Obtain the running image digest and inspect that exact version's wrapper before relying on current upstream defaults. Confirm `archive_mode`, sanitized implementation, `pg_stat_archiver` and spool sizes. The async spool primarily carries archive status; retained WAL commonly remains in `pg_wal`. Do not add WAL and directory totals twice.

If archiving is enabled, verify destination access, successful pushes, full/differential backup cadence and an actual restore test. Keep an explicit recovery window (candidate four weekly fulls and fourteen daily differentials if compatible with the operator's recovery policy), with repository expiry managed by pgBackRest, not object-store deletion of arbitrary WAL. Backup retention in the remote bucket is distinct from local WAL retention. Consider an archive backlog/drop budget of at most 1–2 GiB on this small database, leaving room for relations and recovery, **only after the operator approves the PITR-gap tradeoff**: pgBackRest's queue-max/drop mechanism can sacrifice recoverability to keep Postgres running. Alert well before that budget is reached; do not silently lower it or disable archiving.

Capacity arithmetic is conditional: Oct11 00:00Z to Oct16 06:00Z grew from 4494.11 to 4932.45 MB, ~83.5 MB/day (six-hour averaged samples). Through the last growing sample at Oct16 12:00Z, ~88.6 MB/day; that bucket includes the ENOSPC plateau. Use ~84–89 MB/day as a rough recent trend, not a forecast. At ~5 GB occupied, 20 GB yields roughly 169–180 days to full, 112–120 days to 75%, and 146–156 days to 90%. Backlog catch-up, WAL/archive failures, index growth, new customers and recovery bursts can consume that headroom much faster. Review daily after recovery and budget expansion by the 75% alert. The volume metrics do not prove component attribution.
