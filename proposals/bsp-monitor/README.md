# BSP monitor proposal — not provisioned or enabled

This directory is inert. No Worker, KV, Railway alert, webhook, or secret was created.

Recommended deployment: a small scheduled Cloudflare Worker, in the operator's existing account, independent of BSP's Railway project. Runs every five minutes. Email at 75% and 90% of provisioned capacity, with 70%/85% clearing hysteresis, immediate escalation, recovery email and six-hour reminders. It monitors Postgres, Kafka and ClickHouse volumes. Railway GraphQL `volumeInstances` gives capacity; the checker also reads recent `DISK_USAGE_GB` metrics because the observed `currentSizeMB` snapshot lagged after resize. Missing/stale telemetry is a critical alert, not zero usage. Two successive readiness failures alert (normally within ten minutes, assuming cron delivery); 503, bad JSON, timeout and network failure all count. One successful readiness check resets the failure count. HTTP handlers perform no remediation.

`/health/ready` checks DB and hard dependencies; it does not prove consumer lag, Temporal search attributes, workflow completion or correct billing. Add separate queue-lag/workflow-failure monitors after P6/P8 findings are reconciled.

## Operator application

1. First review/merge/deploy the BSP readiness patch through the actual Railway wrapper source pin. Probe the real HTTPS API `/health/ready`, expecting 200 JSON `status:ok`. Do not configure `/health` here: it cannot detect DB-down.
2. Copy `wrangler.jsonc.example` to `wrangler.jsonc`, set the operator's Cloudflare account ID, real API host, verified Resend sender and on-call email list. Create the dedicated KV namespace `plaqad-bsp-monitor-state` and fill its ID. These are proposed steps, not actions taken by this PR.
3. Set `RAILWAY_API_TOKEN` and `RESEND_API_KEY` with `bunx wrangler secret put <NAME>`. Use a Railway **account/workspace API token** whose access covers only the required project where supported; the code uses `Authorization: Bearer` (not the project-token `Project-Access-Token` header). Keep values in secret bindings only. No customer API key, DB password or connection string is needed. Railway tokens may allow mutations; the code sends only the fixed read-only query. Restrict account membership/access as available.
4. Run `bun test proposals/bsp-monitor/worker.test.mjs` from the repository root. Deploy only after separate operator approval: `bunx wrangler deploy --config wrangler.jsonc` from this directory. Schedule is inactive until that step. Start at one cron instance; KV's eventual consistency is sufficient for ordinary single scheduled operation, but duplicate concurrent invocations can duplicate email. Resend idempotency suppresses identical retries within its retention window, not a global exactly-once guarantee.
5. Verify one healthy run and the monitor `/` heartbeat 200. Exercise threshold and readiness failure using the local tests, not by filling disk/stopping production. Configure an external uptime monitor against this Worker's heartbeat: 503/no recent success for 15 minutes pages on-call through an independent channel. Cloudflare errors/logs also need an owner; Resend or Cloudflare outages cannot reliably report themselves by the same email path. Never log provider response bodies or tokens.

## Railway native option

Railway's [Observability monitors](https://docs.railway.com/observability#monitors) support disk/CPU/RAM/egress threshold email and in-app alerts (Pro plan). Configure per-volume 75% and 90% equivalents: Postgres 15,000/18,000 MB; Kafka 3,750/4,500 MB; ClickHouse 22,500/27,000 MB. Confirm metric units and current resized capacity in UI. Revisit absolute thresholds whenever volume capacity changes. [Project webhooks](https://docs.railway.com/observability/webhooks) carry deployment/crash/restart/volume-usage/monitor events to a chosen receiver; they are complementary, not a DB query probe. [Usage budgets](https://docs.railway.com/pricing/cost-control) warn about spend, not database free space; a spend hard cap that stops billing infrastructure would create another outage. No native settings were changed.

Railway [healthchecks](https://docs.railway.com/deployments/healthchecks) only gate deployments and do not continuously poll after activation. Use `/health/ready` as the API deployment gate after a local dependency-failure smoke; retain `/health` for process liveness in any continuous restart mechanism. A shared DB outage must page/degrade, not restart every API/worker/DB container in a loop.
